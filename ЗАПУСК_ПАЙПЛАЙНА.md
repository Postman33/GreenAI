# Запуск пайплайна от DXF до результата

## Требования

- Python 3.10 или новее;
- Go;
- Docker Desktop с поддержкой `docker compose`.

Команды ниже выполняются в PowerShell из корня проекта.

## Первый запуск

```powershell
Set-Location "F:\Пилотный проект 20 улиц"

py -3.10 -m venv .venv
& .\.venv\Scripts\python.exe -m pip install --upgrade pip
& .\.venv\Scripts\python.exe -m pip install -r .\requirements.txt

go build -buildvcs=false -o .\dxf_extract_go.exe .\parser\dxf_extract_go

docker compose up -d --wait
& .\.venv\Scripts\python.exe .\scripts\seed.py

powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run_pipeline.ps1 `
    -InputDxf ".\Пилотный проект 20 улиц\input_10001759_bound.dxf" `
    -OutputDirectory ".\output" `
    -DxfUnitsPerMeter 1
```

Чтобы выбрать конкретные виды, собственную область и ручные точки, передайте
`-PlantingRequest .\examples\planting_request.json`. Без этого параметра строится
автоматический план по всей рабочей области.

Команды `docker compose` и `seed.py` перед запуском — отдельная однократная подготовка пустой БД. Сам `run_pipeline.ps1` базу не изменяет и при обычной генерации повторно справочники не загружает.

## Повторный запуск

Если окружение, Go-экстрактор и база уже созданы:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run_pipeline.ps1 `
    -InputDxf ".\Пилотный проект 20 улиц\input_10001759_bound.dxf" `
    -OutputDirectory ".\output"
```

Если PostGIS уже работает и его не нужно запускать повторно:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\scripts\run_pipeline.ps1 `
    -InputDxf ".\Пилотный проект 20 улиц\input_10001759_bound.dxf" `
    -OutputDirectory ".\output" `
    -SkipDatabaseStart
```

## Что выполняет скрипт

1. Поднимает PostGIS из `docker-compose.yml`, если не указан `-SkipDatabaseStart`.
2. Извлекает семантические объекты из DXF по `src/core/config.yaml`.
3. Вторым проходом извлекает площадные примитивы по `src/core/surface_inspector_config.yaml`.
4. Нормализует семантические объекты в локальную GeoJSONL-геометрию.
5. Очищает инженерные сети и разделяет их на `CLEAN`, `REVIEW` и `REJECT`.
6. Восстанавливает небольшие разрывы трасс и Т-образные подключения. Параллельные
   линии сохраняются раздельно как возможные границы широкой трубы.
7. Строит диагностические материалы по покрытиям.
8. Формирует базовую область, восстанавливает проезжую часть и вычитает
   фактические круглые контуры существующих колодцев/люков.
9. Читает существующие правила PostGIS и рассчитывает зоны деревьев и кустарников.
10. Проверяет, что зоны не выходят за базовую область и не пересекают дорогу/твёрдые покрытия.
11. Генерирует конкретные точки деревьев и кустарников и площади травянистого покрытия.
12. Копирует исходный DXF и добавляет отдельные слои результата.
13. Проверяет посадки, ссылки на правила и сохранность всех исходных DXF-сущностей.

`run_pipeline.ps1` не выполняет `INSERT`, `UPDATE`, миграции или загрузку справочников в БД.
Итоговый DXF перед повторным запуском нужно закрыть в nanoCAD. Пайплайн использует
строгий экспорт и завершится ошибкой, если указанный файл занят. Это исключает
ситуацию, когда новая версия записалась под другим именем, а проверен старый файл.

## Основные результаты

После успешного запуска в каталоге `output` появятся:

| Файл | Назначение |
|---|---|
| `result_with_planting_plan.dxf` | исходный чертёж с отдельными зонами и конкретными посадками |
| `planting_plan.geojsonl` | паспорт каждой принятой точки/площади: вид, статус, измерения, правило и ссылка на норму |
| `planting_decisions.geojsonl` | решения по всем проверенным точкам, включая отклонённые с причинами |
| `planting_plan_report.json` | число посадок, виды и количество объектов на ручной проверке |
| `plant_allow_zones_debug.png` | быстрая растровая проверка зон и дороги |
| `plant_allow_zones_debug.dxf` | компактный отладочный DXF без всей подосновы |
| `plant_allow_zones.geojsonl` | геометрия допустимых зон деревьев и кустарников |
| `plant_allow_zones_report.json` | применённые и нерешённые нормативные правила |
| `cleaned_utilities.geojsonl` | инженерные линии высокой уверенности до восстановления разрывов |
| `reconstructed_utilities.geojsonl` | очищенные линии вместе с принятыми восстановленными соединениями; этот файл используется нормативными правилами |
| `inferred_utility_connections.geojsonl` | только автоматически достроенные участки с оценкой уверенности |
| `review_utility_connections.geojsonl` | возможные соединения, не прошедшие порог автоматического принятия |
| `network_reconstruction_debug.dxf` | исходные очищенные линии, принятые соединения и кандидаты на проверку на отдельных слоях |
| `network_reconstruction_report.json` | статистика восстановления по типам инженерных сетей |
| `review_utility_graphics.geojsonl` | неоднозначные ветви для ручного подтверждения |
| `rejected_utility_graphics.geojsonl` | распознанные условные знаки и прочая отклонённая графика |
| `utility_cleaning_debug.dxf` | слои `CLEAN_*`, `REVIEW_*` и `REJECT_*` для проверки в nanoCAD |
| `utility_cleaning_report.json` | статистика и причины классификации сетей |
| `constraint_map.geojsonl` | базовая область, покрытия, восстановленная дорога и физические контуры колодцев/люков |
| `constraint_report.json` | площади и диагностика общих ограничений |
| `verification_report.json` | автоматическая проверка пространственных инвариантов |
| `surface_candidates.png` | диагностика найденных площадных слоёв |

Отдельно запустить только восстановление инженерных сетей можно так:

```powershell
.\.venv\Scripts\python.exe .\src\network_reconstructor.py `
    .\output\cleaned_utilities.geojsonl `
    --output .\output\reconstructed_utilities.geojsonl `
    --inferred-output .\output\inferred_utility_connections.geojsonl `
    --review-output .\output\review_utility_connections.geojsonl `
    --report .\output\network_reconstruction_report.json `
    --debug-dxf .\output\network_reconstruction_debug.dxf
```

В `network_reconstruction_debug.dxf` серые слои `SOURCE_*` содержат входные
очищенные линии, голубые `INFERRED_*` — принятые соединения, жёлтые
`REVIEW_GAP_*` — кандидаты для ручной проверки. Параметры находятся в
`src/core/network_reconstructor_config.yaml`.

В `plant_allow_zones_debug.dxf` контекст и рассчитанные зоны разнесены по
отдельным слоям. Для проверки связи посадок с пешеходной инфраструктурой
включите `DEBUG_SIDEWALKS` вместе с `DEBUG_ALLOW_TREE` или
`DEBUG_ALLOW_SHRUB`. Общие твёрдые покрытия находятся на
`DEBUG_HARD_SURFACES`, восстановленная проезжая часть — на
`DEBUG_ROAD_AREA`.

Инженерный контекст вынесен на отдельные слои:

- `DEBUG_WATER_PIPE`, `DEBUG_STORM_DRAIN`, `DEBUG_GAS_PIPE`;
- `DEBUG_HEAT_PIPE`, `DEBUG_SEWER_PIPE`;
- `DEBUG_POWER_CABLE`, `DEBUG_TELECOM_CABLE`, `DEBUG_OVERHEAD_POWER`;
- `DEBUG_CLEAN_WATER_PIPE`, `DEBUG_CLEAN_HEAT_PIPE` — очищенные оси,
  фактически использованные для нормативных буферов;
- `DEBUG_UTILITY_WELLS` — существующие колодцы/люки геоподосновы;
- `DEBUG_UTILITY_WELL_FOOTPRINTS` — фактические круглые пятна колодцев/люков,
  вычтенные из базовой области;
- `DEBUG_UTILITY_MARKERS` — проектные маркеры замены люков;
- `DEBUG_BUILDINGS`, `DEBUG_EXISTING_TREES`,
  `DEBUG_EXISTING_TREE_BELTS`, `DEBUG_VEGETATION`.

Полукруглые вырезы на границе допустимой зоны возникают у концов линейных
коммуникаций: нормативный `buffer` строится с круглым торцом. Наличие объекта
на debug-слое само по себе не означает автоматический запрет — отступ
применяется только при наличии правила со статусом `applied` в
`plant_allow_zones_report.json`.

Для деревьев автоматически применяются 2 м от очищенного водопровода и 2 м от
очищенной теплосети. Для кустарников автоматически применяется 1 м от
очищенной теплосети; числового правила до водопровода в используемой таблице
нет, поэтому оно остаётся `manual_review`. Канализация, водосток, газ, силовые
и телекоммуникационные кабели и ЛЭП также сохраняют `manual_review`.
Автоматические правила инженерных сетей защищены от использования сырой
геометрии: без `reconstructed_utilities.geojsonl` они не выполняются.

В nanoCAD нужно открыть `output\result_with_planting_plan.dxf`. Итоговый DXF открывается с выключенными служебными слоями допустимых зон и восстановленной дороги. Они сохранены в файле и доступны через диспетчер слоёв, но по умолчанию видимы только конкретные посадки и травянистое покрытие. Для диагностического экспорта со всеми зонами используйте у `src/dxf_exporter.py` флаг `--show-analysis-layers`.

В диспетчере доступны слои:

- `GREEN_AI_RECONSTRUCTED_ROAD`;
- `GREEN_AI_ZONE_TREE`;
- `GREEN_AI_ZONE_SHRUB`;
- `GREEN_AI_PLANT_TREE`;
- `GREEN_AI_PLANT_SHRUB`;
- `GREEN_AI_HERBACEOUS`.

Слои `ZONE` показывают допустимые области, `PLANT` — конкретные точки, а
`GREEN_AI_HERBACEOUS` — предложенное травянистое покрытие. Полная интерпретация
каждого объекта находится в `planting_plan.geojsonl`.
